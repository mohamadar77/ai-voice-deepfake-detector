## What this project is

A reproducible graduation project to detect human versus synthesized or
voice-converted speech on ASVspoof 2019 Logical Access (LA). Core: MFCC +
Logistic Regression baseline, a compact log-Mel CNN (clean + one augmented run),
a locked final evaluation with paired robustness and failure analysis, a shared
FastAPI/Streamlit inference path, local Docker packaging and reproducibility
records. One optional stretch (an evaluated evidence assistant / RAG) carries
zero committed hours and is likely deferred. Target presentation: 5 November 2026.

The architecture, module contracts, leakage controls and freeze discipline were
already settled in the documented lead + "Meitner" consultation. The open issues
found in this review are factual/environmental, not architectural.

## Critical findings (the real blockers)

### 1. Documented hardware does not match this machine

`docs/environment.md` describes an Apple M4 Pro, 48 GB RAM, ARM64, ~926 GB disk,
with Metal/MPS. The machine this review ran on is:

- Intel Core i5-1038NG7, 4 physical cores / 8 threads (a 2020 Intel MacBook Pro 13").
- 16 GB RAM, x86_64, no Apple Silicon (confirmed: genuine Intel brand string,
  no Rosetta translation — `sysctl.proc_translated` absent).
- ~470 GB free disk.

These are two different machines, or `environment.md` is wrong. This matters
because the entire effort/compute budget (110–150 h; "4 CNN runs × up to 12
device-hours each"; MPS acceleration) was sized for the M4 Pro. On a 4-core
Intel CPU with no GPU acceleration, the committed CNN run matrix is likely not
feasible without a documented data subset or a different compute target.

### 2. Python 3.12 / PyTorch install is broken locally

- Shell Python is 3.14.6; the project requires 3.12.
- `.venv` points its interpreter at `/tmp/voice-detector-python/...python3.12`,
  which no longer exists (macOS clears `/tmp`). The venv is dead and has no
  dependencies installed — `uv sync` never completed.
- Root cause (already recorded in `docs/data.md`): PyTorch has no macOS x86_64
  wheel for `torch>=2.6` (last Intel-mac build was 2.2.2). So
  `uv sync --frozen` cannot install on this Intel Mac.
- CI passes anyway because it runs on Linux x86_64, where torch wheels exist —
  green CI is masking a locally unusable environment.

### 3. Dataset absent, access unconfirmed

`data/` contains only a README. No ASVspoof audio or protocol files; published-
terms access has not been confirmed or recorded.

3. A persistent Python 3.12 interpreter (not under `/tmp`).
4. Confirmation of actual available hours/week — at 15–20 h/week the full scope
   is not a credible 5 Nov commitment without help or a scope cut.

## Update — implementation session (11 October 2026, later)

Author: implementation session (Claude), same day as the audit above. Unlike the
morning audit, this session **did** create and modify repository files (listed
below) and ran the local toolchain. No dataset, model, checkpoint or evaluation
prediction was downloaded, trained or inspected.

### Decisions recorded this session

- **Compute-target direction chosen:** reserve a **Linux x86_64** machine for all
  training / validation / evaluation. Target spec confirmed available by the
  project owner: **≥20 CPU cores, ≥35 GB RAM, ≥500 GB disk**. This supersedes the
  audit's "compute target undecided" as the single biggest blocker — the direction
  is now set; only the GPU remains open.
- **GPU is optional, not required.** The owner will start **without a GPU** and add
  one later if available, with no code or lockfile change (the locked CUDA `torch`
  for x86_64 runs on CPU and auto-uses a GPU if one is present). CPU-only cost is
  wall-clock on **CNN training only** — estimated a few hours per run on 20 cores;
  the clean + augmented + multi-seed matrix becomes overnight/unattended compute.
  Features, LR baseline, evaluation and API/UI are CPU-native and unaffected.
  Scientific validity and metrics are identical either way.
- **On Linux x86_64 both local install walls disappear** (see reconciliation
  below), so `uv sync --frozen --all-groups` is expected to complete on the
  intended machine and the G0 environment gate can finally pass there.

### Findings reconciled

1. **Hardware (audit finding #1) — confirmed.** This session ran on the Intel Core
   i5-1038NG7 / 16 GB / x86_64 machine, not the M4 Pro described in
   `docs/environment.md`. `environment.md` remains **unreconciled** and should be
   corrected to the reserved Linux machine once it is the recorded target. *(Open.)*
2. **Environment (audit finding #2) — confirmed and widened.** Local
   `uv sync --frozen --all-groups` is blocked on this Intel Mac by **two**
   independent native-wheel walls, both verified this session:
   - `torch>=2.6` / `torchaudio` — no macOS x86_64 wheel in the lock (0 found).
   - `librosa` → `numba` → `llvmlite` — no cp312 macOS x86_64 wheel; the
     `llvmlite` source build fails (needs an LLVM toolchain).

   **Workaround used to make progress today (not a fix):** a torch/librosa-free
   subset install into the project's own `.venv`:
   `uv sync --frozen --all-groups --no-install-package torch
   --no-install-package torchaudio --no-install-package librosa
   --no-install-package numba --no-install-package llvmlite`.
   **No change to `pyproject.toml` or `uv.lock`.** Consequence: `voice-detector
   smoke` fails under the subset env (it imports torch/librosa) — expected; the new
   `protocol-audit` command is stdlib-only and runs. The real fix is the Linux
   x86_64 machine, not this workaround.
3. **Dataset (audit finding #3) — unchanged.** ASVspoof 2019 LA audio and protocol
   files are still absent; access/terms are still to be accepted and recorded in
   `docs/data.md`.
